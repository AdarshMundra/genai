# Lecture 14 Revision

## Overview

This lecture explains **Tool Calling**, which is the process where an LLM decides WHICH tool to use and WHAT arguments to provide, without actually executing the tool itself.

## Key Workflow

### 1. Binding Tools

- You must "bind" your tools to the model so it knows they are available.
- **Code**: `model_with_tools = model.bind_tools([multiply_tool])`

### 2. The Model's Decision

- When you invoke the model, if it decides to use a tool, it returns an `AIMessage` containing a `tool_calls` list.
- Each `tool_call` includes:
    - `name`: The tool's name.
    - `args`: A dictionary of arguments generated by the LLM.
    - `id`: A unique identifier for that specific call.

### 3. Execution (The Developer's Job)

- The model DOES NOT run the code. You must catch the `tool_calls`, execute the corresponding function in Python, and create a `ToolMessage`.

```python
tool_result = multiply.invoke(response.tool_calls[0])
```

### 4. Feeding Back to Model

- To get a final answer, you must send the entire conversation history (HumanMessage + AIMessage with tool_calls + ToolMessage) back to the LLM.

## Advanced: Injected Arguments

- Using `Annotated[type, InjectedToolArg]`, you can define arguments that the LLM shouldn't "see" or "generate" (e.g., a database connection string or a result from a previous tool), but are required by the function.

## Summary

Tool calling is a conversation:

1. **User**: "What is 5 \* 10?"
2. **LLM**: "I need to call the `multiply` tool with `a=5, b=10`."
3. **System**: Runs the function, gets `50`, and tells the LLM.
4. **LLM**: "The answer is 50."
